\section{Ground-truth construction}
\label{sec:groundtruth}

Everything that follows depends on this corpus, so we describe it in more detail than is
usual. Two commitments govern the design. No label comes from a human judgement about
whether a text looks machine-written; labels derive from platform attribution or from
chronology. Positives and negatives are drawn from the same repositories wherever
possible, so that differences between them are not differences between projects.

\input{generated/t_corpus}

Table~\ref{tab:corpus} gives the shape of the result before the detail. Read it one row
at a time. The first row is the positive set: artifacts an agent is declared to have
written, capped at 5{,}000 per genre so that no genre dominates. The second is the
negative set that carries the argument, drawn from the same repositories but committed
before ChatGPT was released, at roughly twice the size so that matching has room to
choose from. The third is a smaller control of human pull requests written during the
agent era, which removes the time gap at the cost of certainty about its labels. The
fourth is pre-ChatGPT output from dependency bots and release automation, which is
machine-written but not model-written, and is what
Section~\ref{sec:validity:rq2:automation} uses to separate the two.

The remaining subsections describe how each set was built.

\subsection{Positive set}
\label{sec:groundtruth:positives}

Positives come from AIDev \citep{li2025aidev}, which collects pull requests opened by
agentic coding platforms operating under their own accounts. We pin the dataset revision
because AIDev is still growing: the paper introducing it reports \citednum{456{,}000}
pull requests, while the revision we analyse contains \AidevPRs{} across \AidevRepos{}
repositories. All counts below are measured from the pinned revision.

Three properties of the positive set bound every claim in this paper. First, the
observation window is seven months: all agent-authored pull requests fall between
\AidevWindowStart{} and \AidevWindowEnd{}, so the results describe the platforms and
model versions current in the first half of 2025. Second, the agent mix is uneven
(Table~\ref{tab:agentmix}). One agent accounts for \AidevTopAgentShare{} of pull requests,
and median body length differs by about an order of magnitude across agents, so any
pooled metric mostly describes that agent. We report detector results per agent, and
give pooled figures only under equal allocation. Third, the texts are short: the median
pull request body is \AidevBodyMedian{} characters and the median commit message
\AidevCommitMsgMedian{}. Detectors that separate classes almost perfectly on
essay-length text are being asked here to decide on a single line of English.

\subsubsection{Artifact genres}
\label{sec:groundtruth:genres}

We treat five genres separately, because they differ in length and register and because
published studies score different subsets of them. Pull request descriptions are prose
of moderate length and often follow a template. Commit messages are the shortest genre
and the most conventional. Issue bodies are prose in a different register from pull
requests. Pull request comments are restricted to human accounts, since
\AidevCommentBotShare{} of comments on agent-authored pull requests come from bots, and
an unfiltered genre would measure continuous-integration output instead of agent output.

The fifth genre needs more explanation than the others. A \emph{code diff} here is the
unified diff of one changed file: the added and removed lines with their surrounding
context, headed by the usual hunk markers. It is not the file's full contents. We score
the change rather than the file because attribution attaches to the change; most lines
of a file were written by somebody else, at some other time, and including them would
dilute whatever authorship signal the contribution carries. Both sides of the comparison
are collected in the same format and matched on length, at a median of
\citednum{877} characters for the positives against \citednum{827} for the negatives, so
no part of the diff result comes from one class being presented differently from the
other.

Scoring code at all deserves a justification, because code is not prose. Its grammar is
fixed, its layout is often decided by a formatter, and its identifiers follow project
convention, so two developers solving the same problem produce far more similar text
than two developers describing it. That is a reason to expect detection on code to be
hard, and it is also why the literature we audit scores code anyway: DetectCodeGPT
exists for exactly this genre, and \citet{ji2026exploratory} apply it to repository code
to produce their headline estimate. An instrument in use is an instrument worth
measuring. Section~\ref{sec:validity:rq1:zeroshot} reports what it does, and
Section~\ref{sec:validity:ceiling} reports how much there was to find in the first
place.

One difference from that literature should be stated here rather than in the results.
\citet{ji2026exploratory} score whole source files; we score diff hunks. A hunk is
shorter and less self-contained, which is the harder setting for any of these
statistics, so our diff numbers are not a direct replication of theirs. The choice
follows from the research question: a prevalence estimate over contributions is an
estimate over changes.

Trailer lines such as \texttt{Co-authored-by} are removed from commit messages before
scoring and stored separately. Recovering an explicit declaration is not detection, and
leaving trailers in place would let a detector identify authorship by reading a label.
The same removal is applied to positive and negative texts, using shared code, so that
normalisation cannot become a signal.

Allocation across the resulting agent-by-genre cells is equal rather than proportional,
targeting 1{,}000 texts per cell with a floor of 300. This trades precision on the
abundant agent for usable precision on the scarce one, which suits a question about
whether detector behaviour generalises across agents. The sampled positive set contains
\PositiveTexts{} texts across \PositiveCells{} cells.

Equal allocation changes the corpus, and the effect should be stated. Because agents
differ in verbosity, reweighting them equally raises the median pull request body from
\PrBodyMedianPopulation{} characters in the population to \PrBodyMedianSampled{} in the
sample. The sampled positive set is therefore not representative of agent contributions,
and we make no estimate of AI prevalence from it. Its purpose is to estimate per-stratum
detector error, which Section~\ref{sec:validity} then applies to representative samples.
Left unstated, the same reweighting would make the detectors look better than they are,
since longer texts are easier to classify.

Issue bodies are the exception to per-agent reporting. They can be attributed to an
agent only through AIDev's issue-to-pull-request link table, and three of the five agent
cells fall below the floor of 300, two of them below 200. We analyse that genre pooled
across agents and restrict per-agent claims to the other four. This reflects what the
attribution data supports.

\subsection{Negative sets}
\label{sec:groundtruth:negatives}

No single negative set is both clean and realistic, so we construct three with
complementary weaknesses.

\subsubsection{N1: pre-LLM artifacts from the same repositories}
\label{sec:groundtruth:n1}

The primary negative set consists of artifacts written in the positive set's own
repositories before \LlmCutoff{}. Its composition follows from chronology, and every
detection in it is a false positive by construction.

Selecting on an artifact's creation date is not sufficient, because bodies can be edited
and issue threads keep accumulating comments. While profiling repository data we found
an issue created in 2013 carrying a comment written in 2026 that opens with an
agent-generated verification report. Selection by creation date alone would have admitted
that comment to a pre-LLM set. We therefore require both the creation and the
last-modification timestamp to precede the cutoff, which shows the text has not been
touched since. The rule is conservative: an old issue touched by a label change is
dropped, which biases the set toward artifacts that attracted no later activity.
Section~\ref{sec:threats} returns to this.

Commit messages and diffs avoid the problem. We read them from cloned repository history
rather than from the platform API, where they are dated by committer timestamp and
cannot be altered without rewriting history. The cutoff is applied in UTC to both the
committer and the author timestamp.

Not every repository has a pre-LLM history. Of the \RepoFrame{} curated repositories,
\NOneResolved{} still resolve on GitHub, \NOneUnresolvable{} having been deleted,
renamed or withdrawn, and \NOneEligible{} of those (\NOneEligiblePct{}) were created
before \LlmCutoff{}. These form the N1 frame, the oldest dating from \NOneOldestRepo{}.
Because repository names can be released on rename and reused, we check that each name
still resolves to the GitHub numeric identifier AIDev recorded and exclude any
repository where it does not, independently of age.

The \NOneExcluded{} excluded repositories are younger than those retained, and younger
projects may differ in how readily they adopt coding agents. Losing this share of the
frame also costs power in the matched analysis. We report a generalisation check on the
excluded repositories using positives alone, to test whether the restriction affects the
conclusions.

\subsubsection{N2: contemporaneous human contributions}
\label{sec:groundtruth:n2}

N1 is clean but separated in time from the positives, which confounds authorship with
period: conventions, tooling and project norms all changed between 2022 and 2025. The
second negative set removes that confound at the cost of certainty. AIDev includes
\AidevHumanPRs{} human-authored pull requests from \AidevHumanRepos{} repositories and
\AidevHumanUsers{} users, drawn from the same period as the positives, with a median
body of \AidevHumanBodyMedian{} characters.

These are attributed to humans rather than verified as human-written. A developer may
have drafted the text with a chatbot and pasted it in, leaving no trace. We therefore
report error rates on N2 as apparent rather than true false positive rates. The
difference between the N1 and N2 rates is informative in itself: under assumptions we
state in Section~\ref{sec:correction}, it bounds how much undeclared assisted authorship
the human population contains.

\subsubsection{N3: pre-LLM automation}
\label{sec:groundtruth:n3}

The third set isolates the confounder. It consists of pre-cutoff artifacts from known
automation accounts, including dependency managers, release tooling and continuous
integration reporters, in the same repositories. This text is machine-generated and
predates large language models. The detection rate on N3 estimates how much reported AI
content is decade-old automation being relabelled.

\subsection{Matching and stratification}
\label{sec:groundtruth:matching}

Detector scores depend on text length, and the agents differ in length, so an unmatched
comparison would partly measure length rather than authorship. We sample negatives to
match the positive length distribution within genre by decile, and report unmatched
results alongside matched ones, since the difference between them estimates the size of
the length effect.

Stratification variables are artifact genre, text length, programming language and
agent. Results are reported along each of them in Section~\ref{sec:validity}.

Two strata named in the study's design do not appear, and both omissions are
deliberate. Project scale would need repository identity on both sides of the
comparison, and while every negative carries one, only a quarter of the positives do,
because agent pull requests reach us through the dataset rather than through a
repository crawl. An analysis over that quarter would describe the projects AIDev
happens to record repository names for. The second is a proxy for contributors' English
proficiency, which \citet{liang2023biased} give good reason to examine. Author-name and
author-location proxies are unreliable and ethically objectionable, and the defensible
alternative, a repository-level measure taken from documentation text, describes a
project rather than a person. We state the gap in Section~\ref{sec:threats} rather than
fill it with a proxy that cannot carry the claim.

We also examined the CrOSSD panel \citep{dam2023crossd} as a source, since it tracks
3{,}255 projects with health and criticality metrics. It stores README text, issue
bodies and issue comments, but records no author, login or actor field on any of them,
so it supports no separation of human from agent from bot and no join to AIDev. The
observation is worth recording for others considering such panels as ground truth: rich
text without author identity cannot serve as an attribution corpus, however large it is.

\subsection{Corpus release}
\label{sec:groundtruth:release}

The corpus is released as a \emph{specification} rather than as a copy of the text.
Redistributing repository content would exceed what the licences of several thousand
projects allow, and a static copy would also hide the thing most worth inspecting, which
is how each cell was selected. What we publish is therefore the recipe and the machinery
to run it:

\begin{itemize}
  \item the artifact identifiers of every text in each cell, with its set, genre and
    matching status, so that any row in any table can be traced to the artifact behind
    it;
  \item the selection predicates and random seeds for each of the four sets, including
    the UTC cutoff comparison, the bot-account list and the exclusion patterns for
    generated and vendored files;
  \item the per-cell counts of Table~\ref{tab:corpus} and the length-matching bins, so a
    rebuild can be checked against the frozen version cell by cell;
  \item the detector harness with each adapter's pinned model weights and revision, and
    the score files those runs produced;
  \item the provenance vocabulary, the RDF graph and the competency queries of
    Section~\ref{sec:provenance}.
\end{itemize}

Code and specification are at
\url{https://github.com/sebneu/ai-authorship-validity}, and an archived release with a
persistent identifier is deposited at \RESULT{Zenodo DOI}. The AIDev dataset
\citep{li2025aidev} is not redistributed; we pin the exact revision used, since the
dataset is live and has roughly doubled since its own publication, and a count taken
from a later revision would not reproduce ours.

One property of the build is worth stating because it is unusual and cheap to adopt.
Every number in this manuscript is written into the \LaTeX{} source by the analysis
scripts as a macro, and a consistency check fails the build if the text contains a
hand-typed figure where a generated one belongs. A stale number cannot survive a re-run
quietly, which is a small guarantee but the appropriate one for a paper about
measurements that were never checked.

\subsection{The detector harness}
\label{sec:groundtruth:harness}

Every instrument is wrapped in one interface: a list of texts goes in, a list of scores
comes out, higher meaning more likely machine-written. Adapters flip the sign of
statistics that natively point the other way, so the direction is the same everywhere.

Detectors see the text and nothing else. The driver passes plain strings rather than a
data frame, so no agent label, repository name, date or set membership can reach an
adapter, and scores are joined back to their rows afterwards. This guard matters because
most fields in the corpus correlate with the label: an instrument shown a 2019 timestamp
would not need to read the text at all.

Scoring models are pinned, and each adapter records the weights it loaded in its version
string. Fast-DetectGPT scores under Qwen2.5-7B, Binoculars under the falcon-7b pair of
its original publication, and DetectCodeGPT under CodeLlama-7b, which is the base model
of its reference implementation and the configuration \citet{ji2026exploratory} deploy.
No commercial detector is included, so the evaluation reproduces from open weights.

Reimplementing DetectCodeGPT surfaced two conflicts between the paper and its released
code, and we record them because they bear on reproducibility in this literature
generally. The paper's Algorithm~1 subtracts a mean of normalised perturbed log rank
terms, which contradicts its own definition of the statistic; and the paper gives a
Poisson mean of two for newline insertion where the released code inserts exactly one,
its Poisson draw commented out. We follow the released code, since it is the artifact
that produced the published numbers, and record the choice in the adapter version
string.
