\section{Results}
\label{sec:validity}

\subsection{How to read the results}
\label{sec:validity:howto}

Every result below compares the same two sets. On one side are artifacts an agent is
declared to have written. On the other are artifacts committed to the same repositories
before ChatGPT was released, matched to the positives on length within genre. Any
artifact a detector flags in the second set is an error, and we know this from the
calendar rather than from a judgement about the text.

Two numbers recur. The area under the ROC curve says how well an instrument ranks agent
text above pre-ChatGPT text; 0.5 is chance, and below 0.5 means the ranking is
backwards. Recall at a fixed operating point says what share of agent artifacts an
instrument recovers once its threshold is set to flag five per cent of pre-ChatGPT text.
The second number matters more in practice, because that is how these instruments are
used: a threshold is chosen and everything above it is counted.

Seven instruments run. Three are the zero-shot detectors the prevalence literature
applies, one is the keyword scan two of the audited studies use, one is a set of
formatting rules of the kind maintainers screen on, one is an instructed language model,
and the last is a classifier we train ourselves as a reference point.

Figure~\ref{fig:auroc} places all of them on one axis. The rest of this section takes
the result apart one question at a time.

\subsection{RQ1: can the instruments tell agent text from human text?}
\label{sec:validity:rq1}

\subsubsection{The zero-shot detectors}
\label{sec:validity:rq1:zeroshot}

\input{generated/t_zeroshot}

Table~\ref{tab:zeroshot} reads one detector per row and one artifact genre per column.
Start with the Binoculars row. Its best genre is a commit message at
\citednum{0.471}, and its worst is a comment at \citednum{0.413}. Both are below 0.5.
Now the Fast-DetectGPT row: commit messages reach \citednum{0.498}, and pull request
bodies fall to \citednum{0.295}.

Every cell in this table is below chance. That is a stronger statement than poor
performance, and it is worth being precise about what it means. A detector at 0.5 is
uninformative. A detector below 0.5 is informative with its sign reversed: in this
corpus, Binoculars and Fast-DetectGPT systematically judge human text written before
ChatGPT existed to be more machine-written than text an agent actually produced.
Fast-DetectGPT on pull request bodies, at \citednum{0.295}, would work as a detector if
its decision were inverted.

\subsubsection{The keyword scan, the formatting rules and the language model}
\label{sec:validity:rq1:others}

\input{generated/t_others}

Table~\ref{tab:others} covers the three remaining candidate instruments. The keyword
scan sits at almost exactly 0.5 in every genre. That is what a detector looks like when
it almost never fires: it is not ranking anything, and Section~\ref{sec:validity:rq1:trade}
takes it apart properly.

The formatting rules do better, from \citednum{0.534} on diffs to \citednum{0.711} on
pull request bodies, and the LLM judge better still, from \citednum{0.619} to
\citednum{0.939}. Both are above chance, so both carry some signal. The pull request
body is where each of them peaks, which is the genre where agent output is most
templated: checklists, headings and summary sections. Section~\ref{sec:validity:rq2:automation}
shows what else those instruments are picking up.

\subsubsection{Is the signal there at all?}
\label{sec:validity:ceiling}

A detector can fail for two reasons. The text may carry no usable signal, or the signal
may be there and the instrument may miss it. Telling these apart needs a classifier that
is allowed to see the training distribution.

We fit gradient-boosted trees on \citednum{24} features computed from the artifact text,
cross-validated in folds grouped by repository so that no project's house style is
learned in training and rewarded in test. Following
\citet{ghaleb2026fingerprinting} we would also have used submission hour and day of
week, and we deliberately do not: those features separate our two classes perfectly
because the negatives predate 2022-11-30 by construction, so a model using them would
measure the corpus design rather than the writing.

\input{generated/t_ceiling}

Table~\ref{tab:ceiling} answers the question. On pull request bodies the classifier
reaches \CeilingAurocMax{}, which is close to perfect separation. On commit messages and
issue bodies it reaches roughly \citednum{0.87}. So the signal is present, and in one
genre it is strong.

Two conclusions follow. For four of the five genres, the zero-shot detectors are not
finding a signal that a modest classifier finds with the same input. Diffs are the
exception: the ceiling there is only \CeilingAurocMin{}, so the difficulty of code is
partly a property of the artifact rather than of the instruments.

\subsubsection{What each instrument recovers in practice}
\label{sec:validity:rq1:recall}

\input{generated/t_recall}

Table~\ref{tab:recall} is the practical version of the same question. Each threshold is
set to flag five per cent of pre-ChatGPT text; the cells say what share of agent
artifacts that buys.

Read the first two rows against the last. Binoculars recovers between
\citednum{1.4} and \citednum{6.0} per cent, and Fast-DetectGPT between \citednum{0.3} and
\citednum{5.7} per cent. Flagging five per cent of artifacts at random would recover five
per cent. Most of these cells are at or below that. The supervised classifier in the last
row recovers up to \CeilingRecallMax{} per cent on the same corpus at the same false
positive rate.

\subsubsection{The keyword scan's trade}
\label{sec:validity:rq1:trade}

\input{generated/t_selfadmission}

Table~\ref{tab:selfadmission} shows why the keyword scan's AUROC of 0.5 is misleading.
Its false positive rate is \SelfAdmissionFprMax{}~per cent in every genre, and its
recall never exceeds \SelfAdmissionRecallMax{}~per cent.

Both numbers follow from the mechanism. The scan searches for tool names such as
ChatGPT or Copilot next to a prefix word. No pre-ChatGPT artifact contains those names,
so there are no false positives at all. Equally, an agent has no reason to write
``generated by ChatGPT'' into its own commit message, so almost nothing is recovered.

This makes the instrument precise and nearly silent. An estimate built on it is a lower
bound, and nothing in the instrument says how far below the truth that bound sits. It is
the exact complement of what \citet{khosravani2026census} find for metadata channels.

\subsection{RQ2: where do the errors come from?}
\label{sec:validity:rq2}

\subsubsection{The instruments respond to automation}
\label{sec:validity:rq2:automation}

Repositories have contained machine-written text for a decade. Dependency bots, release
automation and continuous integration reporters all produce text at scale, and all of it
predates language models. If an instrument flags that text, it is answering a question
about machine authorship in general.

\input{generated/t_automation}

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{figures/f_automation}
\caption{What each instrument flags when no language model was involved. The light bar
is pre-ChatGPT human text, held at five per cent by calibration; the dark bar is
pre-ChatGPT bot output scored at that same threshold.}
\label{fig:automation}
\end{figure}

Table~\ref{tab:automation} and Figure~\ref{fig:automation} give the answer for each
instrument. Every threshold here flags five per cent of pre-ChatGPT human text, so five
per cent is the reference point for every cell.

The LLM judge row is the one to read first. It flags between \JudgeBotFprMin{} and
\JudgeBotFprMax{} per cent of pre-ChatGPT bot output. That is \JudgeBotRatioMin{} to
\JudgeBotRatioMax{} times its rate on human text from the same period and the same
repositories. Asked whether a text was written by AI, it is largely answering whether
the text was written by a machine of any kind. A prevalence estimate produced this way
counts a decade of dependency-update messages as AI adoption.

The formatting rules show the same pattern more weakly, which is what rules matching on
headings and bullet lists should do, since templates produce that structure too.
Binoculars and Fast-DetectGPT do not show it consistently: on issue and pull request
bodies they flag bot text less often than human text.

\subsubsection{Does more text help?}
\label{sec:validity:rq2:length}

Detector statistics are averages over tokens, so they should steady as texts lengthen.

\input{generated/t_length}

Table~\ref{tab:length} splits each genre into five length bands, shortest on the left.
The supervised ceiling behaves as expected, rising from \CeilingShortAuroc{} to
\CeilingLongAuroc{}. The LLM judge and the formatting rules also improve.

Fast-DetectGPT moves the other way, from \FastDetectShortAuroc{} in the shortest band to
\FastDetectLongAuroc{} in the longest. This matters for the common explanation that
these detectors fail on open-source text because the texts are short. If that were the
whole story, the longest band is where they would recover. It is where one of them is
furthest below chance.

\subsubsection{Does any of it generalise across agents?}
\label{sec:validity:rq2:agents}

\input{generated/t_agents}

Because \AidevTopAgentShare{} of AIDev is a single agent, a pooled number would describe
that agent rather than agents in general. The corpus therefore allocates the positive
set equally across the five, and Table~\ref{tab:agents} reports each separately.

The spread across agents within a row is smaller than the spread across genres in the
earlier tables. The failures reported here are a property of the instruments and the
artifact types, not of one platform's house style.

\subsection{RQ3: what does this do to a prevalence estimate?}
\label{sec:correction}

\subsubsection{How much information is left to correct with}
\label{sec:correction:youden}

Equation~\eqref{eq:rogan-gladen} recovers true prevalence from an observed rate, given
sensitivity and specificity. Its denominator is Youden's $J = s + c - 1$, and the
correction divides by it.

\input{generated/t_youden}

Table~\ref{tab:youden} gives $J$ for every instrument and genre. The zero-shot rows are
negative, which follows from Table~\ref{tab:zeroshot}: a detector below chance has a
sensitivity lower than its false positive rate. The keyword scan is positive but tiny,
between \citednum{0.003} and \citednum{0.036}, because it almost never fires. Only the
supervised ceiling and the LLM judge reach values where dividing by $J$ is a sensible
operation.

\subsubsection{When the correction works at all}
\label{sec:correction:estimable}

\input{generated/t_estimable}

Table~\ref{tab:estimable} asks a different question: given a study that reports flagging
some share of artifacts, how often can that share be corrected? Each row is a reported
share, and the three columns count what the estimator returns across all
\CorrectionCells{} instrument and genre combinations.

Take the first row. A study reporting five per cent flagged artifacts can be corrected in
\CorrectionEstimable{} combinations. In \CorrectionUndefined{} the confidence interval
for $J$ covers zero, so the estimator is undefined rather than imprecise. In
\CorrectionOutOfRange{} the correction returns a prevalence above one, which is not a
large estimate but a contradiction: no prevalence between zero and one could produce
that many flags through an instrument with that sensitivity, so the flagged set must
contain something the instrument was not measuring.

Now read down the column. As the reported share rises, the estimable count falls. By
twenty per cent, a figure well within the range these studies report, almost nothing is
left.

\subsubsection{Corrected estimates where they exist}
\label{sec:correction:corrected}

\input{generated/t_corrected}

Table~\ref{tab:corrected} lists every instrument and genre for which a study reporting
twenty per cent flagged artifacts could be corrected at all. The list is short, and the
instruments on it are not the ones the literature uses: the supervised classifier is
ours, and the LLM judge on pull request bodies is the single deployed instrument that
survives.

Where a correction is possible it still moves the number. The ceiling on pull request
bodies corrects a reported twenty per cent to \CeilingCorrectedTwenty{}~per cent
(\CeilingCorrectedTwentyLo{}--\CeilingCorrectedTwentyHi{}).

We make no re-estimate of prevalence on a fresh sample. Doing so would need an
instrument whose $J$ is bounded away from zero on the genre being counted, and
Table~\ref{tab:youden} does not identify one among the detectors the literature uses.
The result of this design is the negative one, together with the measurement that
establishes it.
